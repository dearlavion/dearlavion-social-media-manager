How to configure a project and add channels

A project is a separate brand/business using this tool — its own Drive folders, its own Buffer channels, its own set of social channels. Everything below happens on this dashboard; nothing needs a terminal.

1. Load projects

Fill in the repo Owner/Repo/Branch at the top (already pre-filled by default) and click Load projects. This works with no GitHub token, since the repo is public.

2. Pick a project, or add a new one

Back on the Dashboard, a row of project chips appears — click one to select it. To create a new project instead, go to the Set Up page (left menu) and fill in:

  • Project id — a short slug, lowercase, no spaces (e.g. another-brand). This becomes its folder name on GitHub.
  • Display name — whatever you want shown in the UI (e.g. Another Brand).

Creating a project needs a GitHub token (see below) — it writes a new config/<id>/channels.json to the repo, and switches you to the Dashboard with it selected. Set Up is also where you'll find instructions for connecting a posting tool (Buffer today).

3. Load its channels

Once a project is selected, a Load channels.json for … button appears. Click it to see that project's channel table (empty the first time).

4. Add a channel

Click Add channel, then fill in each field:

FieldWhat it is
EnabledWhether post.yml should post this channel's oldest queued item automatically every time it runs. Leave unchecked while testing a channel you don't want live yet.
IdA unique name for this channel within the project, e.g. ig-main.
PlatformLabel only, for your reference — the real destination is set by Posting tool + its ID field below.
Posting toolWhich backend actually publishes the post. Buffer is the only one implemented today; more can be added later without changing existing channels.
Drive folder IDThe Google Drive folder this channel pulls media from — the long id from the folder's share URL.
Buffer channel IDWhich connected account in Buffer to publish to. Look it up via Buffer's GraphQL API (see the README's Buffer section for the exact query).

Media types: single, carousel, video

There's no separate "media type" field — it's set by how you organize the channel's Drive folder:

  • A loose image or video file at the top level of the folder → a single-item post.
  • A subfolder → a carousel post made from every image/video inside it (up to 10 items — Instagram's cap; more than that is left in inbox/ with a clear log message instead of posting).

Each becomes its own post folder in inbox/<projectId>/<channelId>/<postId>/ once synced. Captions come only from a per-post caption.txt — add one directly to that post's folder on GitHub — Drive sync only picks up image/video files, so this file has to be added on the GitHub side (via the Content Queue's post folder path, or the Contents tab), not through Drive. A post folder with no caption.txt publishes with an empty caption. Any single file over ~90MB is skipped during sync, logged clearly, rather than breaking the run.

5. Save

Click Save to GitHub. This needs a token too. Everything on this page only ever reads or writes what's actually saved on GitHub — edits here aren't used by anything until you save.

Getting a GitHub token

Anything beyond loading (Save, Add project) needs a fine-grained Personal Access Token — add the Actions permission too if you'll use Settings' Trigger now or cron editing:

  1. github.com → your avatar → Settings → Developer settings → Personal access tokens → Fine-grained tokens
  2. Generate new token
  3. Repository access → Only select repositories → this repo
  4. Permissions → Contents: Read and write and Actions: Read and write
  5. Generate, copy it, paste it into the GitHub token field on this page (it stays in this browser tab's session storage — never sent anywhere but api.github.com)

6. Test it

To trigger a run without waiting for its cron, go to Settings (left menu) and use Trigger now on the workflow you want (sync-drive.yml or post.yml) — same as clicking "Run workflow" on the Actions tab, but from this app. Requires a token with the Actions permission (see above). If a channel needs an image and none has been synced from Drive yet, the run's log will say so instead of posting nothing silently.

Common gotchas

  • The repo must stay public — Buffer fetches images from a public GitHub URL, not a binary upload.
  • A 401 on Save/Trigger now almost always means the token field is empty or missing the Actions permission.
  • A 403 on Save usually means the token's repository access was left on a read-only default when it was created.

Using the Content Queue

Content Queue (left menu) has two sections per channel: what's actually waiting in inbox/ ("Synced"), and a lightweight planning checklist sourced from campaigns that are actively running ("Planned").

  1. Load a project's channels on the Dashboard first (Content Queue reuses that same selection).
  2. Switch to Content Queue and click Load queue — this fetches the whole inbox/ tree in a single Git Trees API call (rather than one request per post folder, to stay well under GitHub's 60/hr unauthenticated rate limit) and the project's campaigns.
  3. Synced lists queued posts with a media-type badge (image, video, or carousel ×N), thumbnails, whether it has a custom caption, and its position in that channel's FIFO queue — the oldest one is tagged Posts next run, since each enabled channel's oldest queued item goes out every time post.yml runs.

Synced posts connect to Campaigns: a post already linked to a slot shows a 🎯 Campaign — stage badge; one that isn't linked yet, with an open (planned) slot available for that channel in some campaign, shows a Link to "…" button per candidate slot. Symmetrically, an unlinked Planned row shows a Link media: "…" button per currently-synced post it could claim — same underlying link, reachable from whichever side you're looking at.

Planned only shows campaigns whose status is "ongoing" (set from a campaign's own detail view) — this is deliberately narrower than "every campaign that exists," so Content Queue reflects what you're actively running, not everything you've ever planned. For each channel you can:

  • + Add planned post — pick which ongoing campaign it belongs to, a stage (quick-pick or your own), guidance, and optionally a target date and time — creates a new slot on that campaign directly, without going through the builder.
  • Edit a planned post's stage/guidance/target date/time inline, or Remove it entirely.
  • For an Instagram channel, an Instagram post type dropdown (post / story / reel) also appears — this replaces the old channel-level default entirely, since different planned posts on the same channel often need different types (a reel for one, a regular post for another). It's set per slot, defaults to "post" if left alone, and is what actually gets sent to Buffer once this slot publishes — whether that's through the regular queue or a scheduled time.
  • The target date dropdown is populated from that post's campaign — every day from its start to end date if both are set (e.g. "Sun, Aug 16"), or the next 30 days from today if the campaign has no dates. Date alone stays a pure planning label (a 📅 badge on the row) — nothing enforces it. Add a time too (only enabled once a date is picked) and the slot becomes a real scheduled post — see "Using Scheduled posts" below.
  • Link media: "…" — appears once there's at least one synced post for that row's channel not already claimed by another slot. Clicking it does exactly what the Synced side's Link to "…" does, just started from here.
  • Toggle its todo / done chip — a content-creation checklist ("have I actually made this yet"), separate from the slot's real publish lifecycle (planned → queued → posted). A planned post can be marked "done" (content ready) while still showing up here, right up until it's linked to a synced post and eventually posted.

All of the above needs a token, same as any other save on this page.

Using Scheduled posts

Setting both a target date and a target time on a Planned post turns it into a real scheduled post — this is the one case where a campaign slot actually drives when something publishes, rather than just tracking it.

How it works

  1. .github/workflows/scheduled-posts.yml runs every 5 minutes (unlike the other workflows, which are hourly). Once a slot's target date+time has passed:
  2. If media is already linked (Link media / Link to "…") — it publishes that specific post right away, the same way post.ts would, then marks the slot posted. This does not wait for the channel's usual oldest-file-first turn.
  3. If nothing is linked yet but the post has an "Expected Drive file name" set — before giving up, it looks for a file with that exact name: first among this channel's already-synced-but-unclaimed posts sitting in inbox/, then (if not found there) live in the channel's Drive folder itself, downloading it directly if it finds one. Either way, a match links and publishes immediately, same as the already-linked case above.
  4. If nothing is linked and nothing matches — it logs the message (naming the expected file if one was set), opens a GitHub issue with the full detail, and marks the slot notified (so it won't repeat every run) — the exact same mechanism the Scheduler already uses, no new email service. The run itself only fails (triggering GitHub's backup "workflow run failed" email) if that issue couldn't be opened. Link media (or upload the expected file) before the target time to avoid this.

Naming a file ahead of time

In Content Queue, both "Add planned post" and "Edit" have an optional Expected Drive file name field. Type the exact name you're going to upload (e.g. IMG_1234.jpg), upload it to the channel's Drive folder whenever you get to it, and the scheduled run above finds and links it automatically once the target time arrives — no need to come back and click "Link media" yourself. Matching is exact and case-sensitive (a Drive auto-rename like IMG_1234 (1).jpg won't match), and single-file only — it doesn't match carousel subfolders.

File type is checked against the name's extension before anything else happens — .jpg / .jpeg / .png / .webp for images, .mp4 / .mov / .webm for video (case-insensitive). Something like photo.gif or a name with no extension at all is rejected immediately with a clear "unsupported extension" notification — it never even searches for it, so you're not left wondering why a file that clearly exists in Drive "wasn't found."

Why the regular hourly post run won't post it early

A post folder linked to a slot with a future target time is treated as reserved — the regular post.yml run skips it and posts whatever's next in line instead (or does nothing, if that was the only thing waiting). Once the target time actually passes, the reservation lifts, so if scheduled-posts.yml somehow missed it, the regular flow can still pick it up as a fallback.

Precision

Unlike the Scheduler and the other workflows (hourly), this one checks every 5 minutes — a target time gets acted on (published, or notified as missing media) within a few minutes, not up to an hour late. GitHub's failure-email notification itself is immediate once a check run actually fails; the only real wait is for that next 5-minute check to happen.

Post notifications (success and failure)

Every real publish attempt — whether from post.yml's regular FIFO queue or scheduled-posts.yml's time-scheduled slots — opens a GitHub issue for the outcome, on top of whatever's already logged in the run.

Success

A ✅ Posted: ... issue is opened and immediately closed. You still get a GitHub notification for it (opening any issue does that), it just doesn't sit in your open-issues list forever — close it yourself if you'd rather, but there's no need to.

Failure

If the publisher call itself throws (a Buffer error, a missing token, whatever), a ❌ Post failed: ... issue is opened and left open, with the real error message in the body. The post is left exactly where it was — still in inbox/, or still queued for a scheduled slot — so it's automatically retried the next time that workflow runs, rather than silently lost. The issue is the actual notification; the run only ends up marked failed (triggering GitHub's backup failure email) if that issue itself couldn't be opened — same backup-only pattern as reminders and scheduled-post due-notifications. A post failing doesn't turn the run red by itself, as long as the issue reporting it opened fine.

One channel's failure doesn't block the others

Each channel's publish attempt is handled independently — if channel A fails, channel B still gets its turn in that same run instead of the whole run aborting partway through. Both workflows' "commit posted state" step also runs with if: always(), so whatever did succeed in a run still gets committed even if something else in that same run failed.

Using Campaigns

Campaigns (left menu) plans a push as an ordered sequence of posts and tracks where each one really is — so you have a "what to do next" answer instead of guessing.

1. Build a campaign

  1. Load a project's channels on the Dashboard first (Campaigns reuses that same selection).
  2. Switch to Campaigns, Load campaigns, then New Campaign.
  3. Step 1 — name and goal (start/end dates are optional, informational only).
  4. Step 2 — pick which channel(s) this campaign runs on.
  5. Step 3 — for each channel in scope, optionally set a goal: how many posts you're aiming to actually get published on that channel during this campaign (a live "X/Y slots added" counter next to it tracks how many you've drafted so far — it doesn't block you from adding more or fewer). Then, optionally, add slots in order: pick a stage (quick-pick awareness / consideration / conversion / loyalty for sensible default guidance, or type your own), edit the guidance text, pick a channel, click Add slot. Reorder with the ↑/↓ buttons before moving on. None of this is required — you can create the campaign with zero posts and add them later from Content Queue's "Planned" section.
  6. Step 4 — review the ordered list, then Create campaign (needs a token, same as Save elsewhere).

2. Track it

A campaign's detail view always shows a "What to do next" callout — the first slot that isn't posted yet, with its stage and guidance. Once matching media is synced from Drive, click Load queued posts to see what's currently sitting in inbox/ for that slot's channel (the same data the Content Queue view shows), then Link the right one — the slot flips to queued.

From there it's automatic: when post.yml actually publishes that linked post, post.ts flips the slot to posted and records when, without any manual bookkeeping. If you set a per-channel goal in step 3, the detail view's header shows actual posted count against it (e.g. "3/5 posted toward goal") — purely a progress readout, nothing enforces it. You're not locked into what you set at creation time either — every channel in the detail view has a Set goal / Edit goal button; saving 0 removes the goal entirely.

The channel list itself isn't fixed at creation time either. The Channels section has its own Add channel control (a dropdown of whichever channels aren't in the campaign yet) for bringing in a channel you didn't select in step 1 — it shows up with no goal set, ready for planned posts or a goal. Each channel row also has a Remove channel button, with an inline confirmation that warns if that channel has any planned/queued/posted slots — removing it deletes those slots from the campaign too (the actual synced/posted media in inbox//posted/ is untouched either way).

Further down, All posts lists every slot in the campaign with an Edit button — clicking it switches straight to Content Queue, since that's where a post's stage/guidance actually gets edited (see its "Planned" section above), rather than duplicating that editing UI here too.

The detail view also has a Status dropdown (open / ongoing / done — also shown as a badge on the campaign's card back in the list), an Edit dates control for the start/end dates you set in step 1, a Rename control next to the campaign's name, and an Edit goal control for the campaign's one overall goal text (the "Grow instagram"-style line you set in step 1 -- editable any time after creation too). All four are purely descriptive — set by hand whenever you like, nothing in automation reads or acts on any of them.

Delete campaign removes it entirely, after a confirmation step. If any of its slots are already queued or posted, the confirmation says so — deleting the campaign drops those slots' link back to it, but doesn't touch the actual media sitting in inbox/ or posted/. There's no undo, so double-check before confirming.

Campaigns are a planning/tracking layer only — they don't gate or reorder what actually posts. Each channel's own Enabled setting still decides that, same as always.

Common gotcha

If a linked post gets deleted or moved out of inbox/ by hand instead of through the normal sync → post flow, its slot stays stuck on queued forever — nothing currently detects a broken link. Unlink it manually if that happens.

Using the Scheduler (reminders)

Scheduler (left menu) is a personal reminder calendar, unrelated to any project. It doesn't run its own notification service — it reuses two things GitHub already gives you for free: a workflow-failure email, and issue notifications.

How it works

  1. Click a day on the calendar, set a time, type a message, click Add.
  2. Click Save to GitHub — nothing is real until you save, same as everywhere else in this app.
  3. .github/workflows/reminders.yml runs every hour. If a reminder's date/time has passed and it hasn't fired yet, the workflow logs it clearly, opens a GitHub issue titled with your reminder message, marks it notified, and commits that.
  4. GitHub's normal issue notifications fire for that new issue — that's the actual notification you'll see.

The failure email is a backup, not a second copy

GitHub does not let a workflow put custom text into a "run failed" email's body — it can only say a run failed, with a link. That's why the issue is the primary notification: it's a real GitHub issue with your reminder message as the title and details in the body, so you see the actual content directly instead of having to dig through a run's log. Close the issue once you've handled it.

A separate workflow step only deliberately fails the run — triggering GitHub's built-in "workflow run failed" email — when the issue itself couldn't be opened (a permissions hiccup, an API error). If the issue opens fine, which is the normal case, the run stays green and you get exactly one notification, not two.

Two separate GitHub settings gate whether any of this actually reaches you:

  • github.com/settings/notifications → the Watching and Actions rows should both have your preferred delivery (Email and/or GitHub Mobile push) checked.
  • On the repo itself, the Watch button (top of the repo page, next to Star) — if it's on the default "Participating and @mentions", a new issue opened by github-actions[bot] (not you) won't notify you at all, since you're neither the author nor mentioned. Switch it to All Activity to actually receive these.

Content Queue's planned posts also show up here

Load calendar loads reminders and every project's Content Queue "Planned" posts that have a target date — a lavender dot marks any day with at least one, next to the green reminder dot. Click that day to see the campaign, stage, project, and channel for each one.

This is exactly the same set Content Queue's own "Planned (ongoing campaigns)" list shows: the slot's campaign must be ongoing, and the slot itself must still be planned (not yet linked to media or posted) — so it disappears from the calendar the moment it's linked in Content Queue, same as it does there. It's read-only on this page — edit dates, guidance, or links from Content Queue or Campaigns instead.

Using Settings (workflow schedules)

Settings (left menu) controls how often sync-drive.yml, post.yml, reminders.yml, and scheduled-posts.yml run. There's no separate GitHub API for a workflow's schedule — it lives as a cron: line inside that workflow's own YAML file on main — so this page reads that file, lets you change the schedule, and commits it straight back, the same way every other Save button in this app edits a file on GitHub.

How it works

  1. Load schedules reads all four workflow files and shows each one's current cron as plain English (e.g. "Every hour, at :15" or "Weekdays at 09:30").
  2. Each card has a Schedule type dropdown with three options, freely switchable — nothing is locked to one shape:
    • Every hour, at a specific minute (0–59) — the default for the three hourly workflows.
    • Every N minutes (1/5/10/15/20/30/60) — the default for scheduled-posts.yml, since it polls rather than firing once an hour — see Scheduled posts.
    • On specific days, at a specific time — an hour + minute, plus a day-of-week picker (Every day / Weekdays / Weekends presets, or check individual days). Useful if a workflow should only run on, say, weekday mornings instead of around the clock every hour.
  3. Save schedule commits just that one change to the workflow file — everything else in it (secrets, steps, triggers) is left untouched.
  4. Trigger now runs that workflow immediately (same as clicking "Run workflow" on GitHub's Actions tab) without changing its schedule at all — handy for testing right away instead of waiting for it.

No seconds, ever

GitHub Actions cron simply has no seconds field — minute, hour, day, month, weekday, that's the whole syntax. One minute is the finest granularity possible, regardless of what this page offers or how it's configured.

Why the hourly workflows default to different minutes

sync-drive, post, and reminders ship offset from each other (:00, :15, :30) on purpose — each run ends with an auto-commit (synced media, moved post folders, or a notified reminder), and two workflows committing around the same moment can occasionally collide. Setting two of them to the same minute here shows a small heads-up under both cards — it's not blocked, just flagged, since an occasional collision on a personal-scale repo is a minor inconvenience, not a real problem. This heads-up compares minutes across the hourly and days-at-time patterns alike (whichever ones have a single fixed minute) — scheduled-posts.yml's own every-N-minutes interval isn't a single minute, so it's left out of the comparison.

If a schedule looks read-only

This page only recognizes the three cron shapes above. If a workflow file were ever hand-edited into some other cron expression — a day-of-month restriction, a month restriction, an hour range — its card shows the raw value instead of an editable field, rather than risk saving something mangled. Edit that one directly in the repo if it ever needs to change.

Permissions

Save schedule needs the same Contents: read and write token as every other Save button in this app. Trigger now additionally needs Actions: read and write, since it calls a different GitHub API to dispatch a run.
