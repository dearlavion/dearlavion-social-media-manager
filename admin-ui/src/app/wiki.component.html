How to configure a project and add channels

A project is a separate brand/business using this tool — its own Drive folders, its own Buffer channels, its own set of social channels. Everything below happens on this dashboard; nothing needs a terminal.

1. Load projects

Fill in the repo Owner/Repo/Branch at the top (already pre-filled by default) and click Load projects. This works with no GitHub token, since the repo is public.

2. Pick a project, or add a new one

Back on the Dashboard, a row of project chips appears — click one to select it. To create a new project instead, go to the Set Up page (left menu) and fill in:

  • Project id — a short slug, lowercase, no spaces (e.g. another-brand). This becomes its folder name on GitHub.
  • Display name — whatever you want shown in the UI (e.g. Another Brand).

Creating a project needs a GitHub token (see below) — it writes a new config/<id>/channels.json to the repo, and switches you to the Dashboard with it selected. Set Up is also where you'll find instructions for connecting a posting tool (Buffer today).

3. Load its channels

Once a project is selected, a Load channels.json for … button appears. Click it to see that project's channel table (empty the first time).

4. Add a channel

Click Add channel, then fill in each field:

FieldWhat it is
EnabledWhether the hourly cron should pick this channel up automatically. Leave unchecked while testing — the per-row Post now button ignores this anyway.
IdA unique name for this channel within the project, e.g. ig-main.
PlatformLabel only, for your reference — the real destination is set by Posting tool + its ID field below.
Posting toolWhich backend actually publishes the post. Buffer is the only one implemented today; more can be added later without changing existing channels.
Interval (h)How many hours must pass since the last post before this channel is due again.
Drive folder IDThe Google Drive folder this channel pulls media from — the long id from the folder's share URL.
Buffer channel IDWhich connected account in Buffer to publish to. Look it up via Buffer's GraphQL API (see the README's Buffer section for the exact query).
IG post typeInstagram only — post, story, or reel. Defaults to post.
Caption templateDefault caption text for every post on this channel, unless a post's folder has its own caption.txt (see below).

Media types: single, carousel, video

There's no separate "media type" field — it's set by how you organize the channel's Drive folder:

  • A loose image or video file at the top level of the folder → a single-item post.
  • A subfolder → a carousel post made from every image/video inside it (up to 10 items — Instagram's cap; more than that is left in inbox/ with a clear log message instead of posting).

Each becomes its own post folder in inbox/<projectId>/<channelId>/<postId>/ once synced. To give one specific post a custom caption instead of the channel's default template, add a caption.txt file directly to that post's folder on GitHub — Drive sync only picks up image/video files, so this file has to be added on the GitHub side (via the Content Queue's post folder path, or the Contents tab), not through Drive. Any single file over ~90MB is skipped during sync, logged clearly, rather than breaking the run.

5. Save

Click Save to GitHub. This needs a token too. Everything on this page only ever reads or writes what's actually saved on GitHub — edits here aren't used by anything until you save.

Getting a GitHub token

Anything beyond loading (Save, Add project, Post now) needs a fine-grained Personal Access Token:

  1. github.com → your avatar → Settings → Developer settings → Personal access tokens → Fine-grained tokens
  2. Generate new token
  3. Repository access → Only select repositories → this repo
  4. Permissions → Contents: Read and write and Actions: Read and write
  5. Generate, copy it, paste it into the GitHub token field on this page (it stays in this browser tab's session storage — never sent anywhere but api.github.com)

6. Test it

Two ways to trigger a post without waiting for the hourly cron, both requiring the token above:

  • Post now (per channel row, next to Remove) — forces just that one channel, ignoring its Enabled checkbox and interval entirely. The fastest way to test a single new channel.
  • Post now (all channels in …) — runs the same sync-then-post flow for every enabled, due channel in the currently selected project only.

Either can take up to a couple of minutes — the status message at the top updates as each step (sync, then post) finishes. If a channel needs an image and none has been synced from Drive yet, it'll say so instead of posting nothing silently.

Common gotchas

  • The repo must stay public — Buffer fetches images from a public GitHub URL, not a binary upload.
  • A 401 on Save/Post now almost always means the token field is empty or missing the Actions permission.
  • A 403 on Save usually means the token's repository access was left on a read-only default when it was created.

Using the Content Queue

Content Queue (left menu) has two sections per channel: what's actually waiting in inbox/ ("Synced"), and a lightweight planning checklist sourced from campaigns that are actively running ("Planned").

  1. Load a project's channels on the Dashboard first (Content Queue reuses that same selection).
  2. Switch to Content Queue and click Load queue — this fetches the whole inbox/ tree in a single Git Trees API call (rather than one request per post folder, to stay well under GitHub's 60/hr unauthenticated rate limit) and the project's campaigns.
  3. Synced lists queued posts with a media-type badge (image, video, or carousel ×N), thumbnails, whether it has a custom caption, and a rough ~estimated next-post time based on lastPostedAt + intervalHours — a real Post now run or the hourly cron can shift it.

Synced posts connect to Campaigns: a post already linked to a slot shows a 🎯 Campaign — stage badge; one that isn't linked yet, with an open (planned) slot available for that channel in some campaign, shows a Link to "…" button per candidate slot. Same link Campaigns' own detail view creates (see below) — just reachable from whichever side you're looking at.

Planned only shows campaigns whose status is "ongoing" (set from a campaign's own detail view) — this is deliberately narrower than "every campaign that exists," so Content Queue reflects what you're actively running, not everything you've ever planned. For each channel you can:

  • + Add planned post — pick which ongoing campaign it belongs to, a stage (quick-pick or your own), guidance, and optionally a target date — creates a new slot on that campaign directly, without going through the builder.
  • Edit a planned post's stage/guidance/target date inline, or Remove it entirely.
  • The target date dropdown is populated from that post's campaign — every day from its start to end date if both are set (e.g. "Sun, Aug 16"), or the next 30 days from today if the campaign has no dates. It's purely a planning label shown as a 📅 date badge on the row — nothing enforces it or uses it to decide when a post actually goes out; that's still intervalHours and the cron.
  • Toggle its todo / done chip — a content-creation checklist ("have I actually made this yet"), separate from the slot's real publish lifecycle (planned → queued → posted). A planned post can be marked "done" (content ready) while still showing up here, right up until it's linked to a synced post and eventually posted.

All of the above needs a token, same as any other save on this page.

Using Campaigns

Campaigns (left menu) plans a push as an ordered sequence of posts and tracks where each one really is — so you have a "what to do next" answer instead of guessing.

1. Build a campaign

  1. Load a project's channels on the Dashboard first (Campaigns reuses that same selection).
  2. Switch to Campaigns, Load campaigns, then New Campaign.
  3. Step 1 — name and goal (start/end dates are optional, informational only).
  4. Step 2 — pick which channel(s) this campaign runs on.
  5. Step 3 — for each channel in scope, optionally set a goal: how many posts you're aiming to actually get published on that channel during this campaign (a live "X/Y slots added" counter next to it tracks how many you've drafted so far — it doesn't block you from adding more or fewer). Then, optionally, add slots in order: pick a stage (quick-pick awareness / consideration / conversion / loyalty for sensible default guidance, or type your own), edit the guidance text, pick a channel, click Add slot. Reorder with the ↑/↓ buttons before moving on. None of this is required — you can create the campaign with zero posts and add them later from Content Queue's "Planned" section.
  6. Step 4 — review the ordered list, then Create campaign (needs a token, same as Save elsewhere).

2. Track it

A campaign's detail view always shows a "What to do next" callout — the first slot that isn't posted yet, with its stage and guidance. Once matching media is synced from Drive, click Load queued posts to see what's currently sitting in inbox/ for that slot's channel (the same data the Content Queue view shows), then Link the right one — the slot flips to queued.

From there it's automatic: when post.yml actually publishes that linked post, post.ts flips the slot to posted and records when, without any manual bookkeeping. If you set a per-channel goal in step 3, the detail view's header shows actual posted count against it (e.g. "3/5 posted toward goal") — purely a progress readout, nothing enforces it. You're not locked into what you set at creation time either — every channel in the detail view has a Set goal / Edit goal button; saving 0 removes the goal entirely.

Further down, All posts lists every slot in the campaign with an Edit button — clicking it switches straight to Content Queue, since that's where a post's stage/guidance actually gets edited (see its "Planned" section above), rather than duplicating that editing UI here too.

The detail view also has a Status dropdown (open / ongoing / done — also shown as a badge on the campaign's card back in the list) and an Edit dates control for the start/end dates you set in step 1. Both are purely descriptive — set by hand whenever you like, nothing in automation reads or acts on either one.

Campaigns are a planning/tracking layer only — they don't gate or reorder what actually posts. Each channel's own Enabled/Interval (h) settings still decide that, same as always.

Common gotcha

If a linked post gets deleted or moved out of inbox/ by hand instead of through the normal sync → post flow, its slot stays stuck on queued forever — nothing currently detects a broken link. Unlink it manually if that happens.

Using the Scheduler (reminders)

Scheduler (left menu) is a personal reminder calendar, unrelated to any project. It doesn't send its own email — it reuses GitHub's built-in workflow-failure notification, since that's already something GitHub emails you for free.

How it works

  1. Click a day on the calendar, set a time, type a message, click Add.
  2. Click Save to GitHub — nothing is real until you save, same as everywhere else in this app.
  3. .github/workflows/reminders.yml runs every hour. If a reminder's date/time has passed and it hasn't fired yet, the workflow logs it clearly, marks it notified, commits that, and then deliberately fails the run.
  4. GitHub's own "workflow run failed" email notification fires because of that failure — nothing custom-built.

The one real limitation

GitHub does not let a workflow put custom text into that notification email's body — it can only say a run failed, with a link. Your actual reminder message is only visible by clicking through to the failed run and opening the Check reminders step's log, where it's the first line, clearly marked. This is a trade-off for using a free mechanism that already exists rather than adding a whole email-sending service.

Also check github.com/settings/notifications → the Actions section has email notifications enabled (usually on by default for repos you own) — otherwise GitHub won't email you about the failure at all.
